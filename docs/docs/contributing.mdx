# Contributing to the documentation

These guidelines explain how to contribute to the FoundryEngine documentation. You can contribute by forking the repository and opening a pull request on GitHub.

Run the website locally with [npm]. Use a Node Version Manager like [nvm] (Mac, Linux) or [nvs] (Windows) to install Node and npm. Run these commands from the `docs/` directory:

```bash
nvm use # or nvs use on Windows
npm install
npm run start
```

## Documentation principles

The documentation explains how to implement concepts in FoundryEngine and Minecraft.

- **It is not a tutorial.** It does not provide code for copy-pasting. Use external videos or guides for tutorials.
- **It is not an API reference.** Descriptions clarify guides, but class documentation belongs in [Parchment for Minecraft][parchment] or [NeoForge][neo].
- **It does not explain Java.** Readers must have basic knowledge of Java and Groovy. Link to original resources for complex language concepts.

## Content structure

Content is in `docs/docs/` under three folders: `getting-started`, `guides`, and `concepts`. Each page covers one concept. Split large concepts into sub-concepts on separate pages.

### Concepts and guides
Introduce the concept, its use in Minecraft or the engine, why it is used, and how to use it. Use headers for each section. Divide sections into sub-sections when needed.

Link to other concepts. Include a summary or example to explain the relationship.

### Examples
Code examples use pseudocode to explain concepts. Pseudocode uses the syntax and structure of the language but uses comments as placeholders for implementation logic. Lines must use valid syntax even if the block is not compilable.

Guides cover general use cases. Use a full code example if pseudocode is unclear. Provide dummy values and explain their purpose.

For a method like `#applyDiscount`, the pseudocode uses a comment to describe the logic:

```java
// In some class
public float applyDiscount(float price) {
    float newPrice = price;
    // Apply discount to newPrice
    return newPrice;
}
```

## Style guide

The documentation uses [Docusaurus][docusaurus] and [MDX][mdx].

### Front matter
Front matter defines page metadata with `---` delimiters. Define `sidebar_position` to set the page order. The site parses the `title` and `description` from the page content.

### Categories
Folders represent categories. They inherit titles and positions from `index.mdx`. If no `index.mdx` exists, create a `_category_.json` file with `label` and `position` fields.

### Titles
Use up to six hashtags (`#`) for titles. Titles use sentence case. Headings must be specific; avoid generic titles like "Overview" or "Summary".

### Diction
Use American English. Do not use contractions. Avoid pronouns like "I", "me", or "you" unless referring to the reader. Limit the use of demonstratives like "this" or "that". Use specific nouns.

Follow these writing requirements:
- **Use simple verbs:** Use "is", "has", or "does". Avoid "serves as", "features", or "showcases".
- **Avoid promotional language:** Do not use words like "powerful", "amazing", or "revolutionary".
- **Avoid AI-associated terms:** Do not use "leverage", "robust", "comprehensive", "seamless", "delve", or "tapestry".
- **No meta-narration:** Do not use phrases like "Let's take a look", "In this guide", or "It is worth noting".
- **Limit em dashes:** Use no more than one em dash per 1000 words.

### Formatting
- **Paragraphs:** Use continuous blocks separated by a blank line. Do not put every sentence on a new line.
- **Indentation:** Use four spaces. Do not use tabs.
- **Emphasis:** Use **bold** for importance and _italics_ for terminology.
- **Lists:** Use `-` for unordered lists and `1.` for ordered lists.
- **No placeholders:** Do not leave placeholders or "TODO" notes in published pages.

### Code references
Surround code elements with backticks. Use simple names for classes. Methods and fields include the class name followed by `#`. Prefix with `#` if the class is implied. Inner classes use a `.` after the outer class name.

Code blocks specify the language after the triple backtick. Use `json5` for JSON to allow comments.

### Links
Links use the reference style with brackets. Define the URL at the bottom of the page.

### Diagrams
Create diagrams with the [Mermaid library][mermaid]. Abstract classes are red and non-abstract classes are blue.

## Verification

Check API calls against the source code before publishing:

- **Builders:** `src/main/java/de/luckymcdev/foundryengine/common/builder/`
- **Events:** `src/main/java/de/luckymcdev/foundryengine/common/event/`
- **Managers:** `de.luckymcdev.foundryengine.common.Common`
- **Examples:** `ExampleBundles/` and `TestBundle/`

Run `npm run docs:build` to check for broken links. Fix every failure before opening a pull request.

## Versioning

The live folder documents the current Minecraft version. Do not edit versioned copies. Edit the live folder and freeze a new version with `npm run docs:version <version>`.

# Bundles to registry pipeline

A bundle is text on disk. What Minecraft sees is content in registries and JSON files. This page walks the path in between.

## Step 1: The engine discovers the bundle

At startup the engine scans the bundle directory for folders with one `.bundles.toml` file. Each one becomes a `Bundle` with an id, a version, and its script folders. Entrypoints are ordered by priority within their script environment.

## Step 2: Scripts register content

The engine instantiates one entrypoint object per script folder and calls `onLoad()`. Inside, your code builds content with the builders and hands it to `BundleEvents.registry`:

```groovy
def gem = ItemBuilder.create(id("magic_gem")).stacksTo(16)
BundleEvents.registry {
    it.items(gem)
}
```

The registry callback runs during NeoForge registry registration. The `RegistryEvent` wrapper provides methods for items, blocks, recipes, sounds, particles, tags, and other supported content; each method applies its own side and compatibility checks.

## Step 3: The data generator writes JSON

The engine runs its bundle data generator during common setup after registry collection. It writes server data and, on the client, client assets under the engine's generated bundle output directory. There is no `runData` task for this runtime bundle generator.

Two consequences follow from this split:

- **Registration and generated files are separate.** Builder methods such as `generateData(false)` leave those files to the bundle author.
- **Generated files are output.** Hand-authored bundle assets and data remain alongside the scripts; generated files are stored under the engine's temporary bundle output path and exposed as a resource pack.

## Step 4: The game runs the bundle

Once registered, content behaves like native content. Items render, blocks place, recipes craft. Runtime features like areas and waypoints are not registry entries at all; they are state the managers keep and save.
